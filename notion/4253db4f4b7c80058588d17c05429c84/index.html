一、数据分块（Chunking）

1. 如何根据文档类型（财报 vs. 聊天记录）选择分块策略？

我会根据文档的结构特征、语义关联性以及实际检索需求来选择分块策略，而不是对所有文档统一采用固定长度切分。

文档类型 推荐分块方式 原因
财务报告 按章节、标题、表格切分 保留财务指标及其业务背景
聊天记录 按对话轮次、主题切分 避免将问题和回答拆开
技术文档 按标题层级、代码块切分 保证技术概念与代码示例完整
医学文献 按章节、段落切分 保留医学知识及其适用条件
普通长文本 固定长度 + 滑动窗口 实现简单，适合大规模处理
法律文档 按条款、章节切分 保证法律条款及限定条件完整

例如，财报具有非常明显的结构化特征，我会优先按照章节和标题进行分块，并尽量保持表格的完整性。而对于聊天记录，由于上下文存在较强的依赖关系，我会按照问答轮次或者对话主题切分，避免将用户的问题与对应的回答分到不同的数据块中。

核心原则是让每一个 Chunk 尽可能成为一个可以独立理解、独立检索的语义单元。

2. 为什么很多系统采用“固定大小 + 部分语义切分”的折中方案？

纯固定大小切分虽然计算成本低，但是容易破坏语义完整性；而基于 Embedding 相似度或者大模型的纯语义分块，虽然能够更好地识别主题变化，但是在大规模文档处理时会带来较高的计算成本，而且生成的数据块长度不容易控制。

因此，实际工程中通常采用递归文本切分（Recursive Text Splitting）配合块大小限制和重叠窗口。

例如，设置 Chunk Size 为 512 Token、Chunk Overlap 为 64 Token，优先按照章节、段落、句子进行切分，如果某个段落仍然超过最大长度，再进一步拆分。

这样既能控制每个 Chunk 的大小，又能够通过语义边界和重叠窗口减少上下文信息丢失，同时避免纯模型语义分块带来的大量计算开销。

需要注意的是，256～512 Token 只是常见的实验起点，并不是最优的固定标准。实际需要结合 Embedding 模型、文档类型和 Recall@K 等检索指标进行调优。

二、向量库与索引

1. 能否解释 HNSW 的关键参数 M、efConstruction、efSearch 如何影响索引构建成本、查询延迟和召回率？

首先需要理解 HNSW（Hierarchical Navigable Small World，分层可导航小世界图）的基本原理。

HNSW 是一种基于多层图结构的近似最近邻搜索（ANN）算法。它类似于跳表，通过上层图进行快速定位，再通过下层图进行精细搜索，从而避免遍历所有向量。

HNSW 主要有三个关键参数：

参数 含义 增大后的影响
M 控制每个节点的邻居连接数量 内存增加、构建成本增加，通常提高召回率
efConstruction 构建索引时的候选搜索范围 构建速度变慢、图结构质量通常提高
efSearch 查询时的候选搜索范围 查询延迟增加、召回率通常提高
  • M：控制图的连接密度。 每个节点拥有更多邻居，搜索时就有更多可选择的路径，不容易陷入局部最优，但是需要额外的内存存储连接关系。
  • efConstruction：控制建图时的搜索精细程度。 在插入一个新的向量时，搜索更多的候选节点，从而找到更合适的邻居，代价是索引构建时间增加。
  • efSearch：控制查询时的搜索精细程度。 搜索时保留更多候选节点，能够降低遗漏真实近邻的概率，但是会增加距离计算次数和查询延迟。

在实际项目中，我会先根据内存预算确定 M，再根据离线构建时间确定 efConstruction，最后通过调整 efSearch，在满足 P99 延迟要求的前提下尽可能提高 Recall@K。其中 M 和 efConstruction 通常需要在构建索引时确定，而 efSearch 可以在查询阶段调整，因此它是线上性能调优的重要参数。

2. 补充：HNSW、IVF、PQ 应该如何选择？

技术 核心思想 优点 缺点
Flat 暴力遍历所有向量 精确检索 大规模查询成本高
HNSW 通过多层图进行搜索 高召回、低延迟 图结构占用内存
IVF 将向量聚类，只搜索部分簇 减少搜索范围 可能遗漏其他簇的近邻
PQ 将高维向量分段量化压缩 大幅减少存储成本 存在量化误差
IVF-PQ 聚类搜索结合向量压缩 适合大规模数据 参数调优复杂

如果是中小规模、对召回率和查询速度要求较高的系统，我会优先考虑 HNSW。如果数据规模非常大，而且内存资源有限，我会考虑 IVF-PQ，通过缩小搜索范围和向量压缩降低资源成本。

需要注意的是，IVF 并不一定比 HNSW 更快，PQ 也不是与 HNSW 完全互斥的索引结构。具体性能取决于数据分布、向量维度、参数配置和硬件资源。

三、检索与融合（Hybrid Search）

1. 为什么需要混合检索？

因为单纯的向量检索和单纯的关键词检索都存在局限性，两者具有一定的互补性。

第一，稀疏检索（Sparse Retrieval）。 以 BM25 为代表，通过词频、逆文档频率、文档长度等信息计算相关性，擅长匹配专业术语、产品编号、错误代码等精确词汇，但对于同义词和语义相近的表达，检索能力相对有限。

第二，稠密检索（Dense Retrieval）。 通过 Embedding 模型将文本转换为向量，再计算向量之间的相似度，能够理解文本的语义关系，但是可能无法准确区分低频专业术语、数字和相似实体。

例如，在一个烧伤医学知识库中：

用户问题 BM25 向量检索
VSS 评分标准是什么？ 擅长匹配 VSS 可能召回其他瘢痕评分标准
烧伤愈合后皮肤凸起怎么办？ 可能缺少对应关键词 能够理解增生性瘢痕相关语义
TBSA 10% 的患者如何评估？ 擅长匹配 TBSA 等词汇，但依赖分词 不一定能够准确区分数值条件

因此，我会使用混合检索，同时执行 BM25 和向量检索，再将两路结果融合，既保证专业术语的精确匹配，又保证自然语言问题的语义召回。对于必须严格匹配的数值、编号等条件，还可以引入元数据过滤。

2. RRF 相比人工加权的好处是什么？

传统的人工加权融合通常采用如下公式：Score=αSBM25+(1−α)SvectorScore=\alpha S_{BM25}+(1-\alpha)S_{vector}Score=αSBM25​+(1−α)Svector​

但是 BM25 和向量检索的评分体系不同。例如，BM25 的得分可能是 15.8，而余弦相似度可能是 0.85，直接进行加权是不合理的，需要先进行分数归一化，再通过实验确定权重。

RRF（Reciprocal Rank Fusion，倒数排名融合）解决了这个问题。它不关心原始分数，而是根据文档在不同检索结果中的排名计算融合得分。

RRF(d)=∑i=1n1k+ranki(d)RRF(d)=\sum_{i=1}^{n}\frac{1}{k+rank_i(d)}RRF(d)=i=1∑n​k+ranki​(d)1​

其中，d 是候选文档，n 是检索器数量，ranki(d)rank_i(d)ranki​(d) 是文档在第 i 个检索器中的排名，k 是平滑常数，常见取值为 60。未被某一路检索召回的文档，在该路不产生得分。

RRF 的主要优势是避免不同检索器之间的分数尺度不一致问题，不需要进行复杂的分数归一化，也不需要为每一路检索器人工指定权重，具有较好的通用性。

但是 RRF 也有缺点，它忽略了原始分数之间的差距。例如排名第一和第二的文档，可能原本具有非常大的相关性差距，而 RRF 只考虑名次差距。此外，RRF 并不是完全无参数的算法，它仍然存在平滑常数和候选窗口大小等参数。

3. 如何在不显著增加延迟的前提下接入 BM25？

我会从并行执行、索引选型、候选数量和超时降级四个方面进行优化。

首先，采用异步并行检索。 BM25 和向量检索之间没有直接依赖关系，因此可以同时执行，而不是等待一路检索完成后再执行另一路。

其次，可以选择 Elasticsearch 等同时支持全文检索和向量检索的系统，减少维护两套独立检索服务的成本。两路检索只需要返回有限的 Top-K 候选文档，不需要返回大量结果。

最后，为不同检索器设置超时机制。如果某一路检索超时，可以根据业务要求降级为单路检索，避免整个 RAG 请求被慢服务阻塞。实际生产中还需要使用独立线程池、并发限制和异常处理，上面的代码仅展示并行执行的核心逻辑。

四、重排序与上下文压缩（Re-ranking）

1. Re-ranker 与 Bi-encoder 在结构和能力上的本质区别是什么？

两者最核心的区别在于：Query 和 Document 是独立编码，还是联合编码。

对于 Bi-encoder，Query 和 Document 分别通过编码器生成向量，然后通过余弦相似度或者内积计算相关性。由于 Document 向量可以提前计算，因此适合百万级甚至亿级文档的快速检索。

而 Cross-encoder 会将 Query 和 Document 拼接后输入同一个 Transformer 模型，通过 Attention 机制充分学习两个文本之间的细粒度语义关系，直接输出相关性得分，因此通常具有更好的排序能力，但无法像 Bi-encoder 那样提前计算独立的文档向量来完成检索。

对比维度 Bi-encoder Cross-encoder
输入方式 Query、Document 独立输入 Query、Document 联合输入
输出 Embedding 向量 相关性得分
文本交互 向量层面 Token 层面
文档特征预计算 可以 无法预计算完整匹配得分
查询速度 快 相对较慢
匹配精度 相对较低 通常较高
使用阶段 初步召回 精细排序

为什么不直接使用 Cross-encoder 进行检索？ 假设知识库中存在 100 万篇文档，如果直接使用 Cross-encoder，就需要针对当前 Query 和每篇文档分别执行相关性推理，计算成本非常高。因此实际系统通常采用两阶段架构，先使用 Bi-encoder 快速召回几十篇候选文档，再使用 Cross-encoder 对候选文档进行精细排序。

2. 如何选择 Re-ranker 模型？

我主要考虑以下几个方面：

考虑因素 选择依据
语言支持 中文知识库需要较好的中文或多语言能力
领域适配 医疗、金融等专业场景需要评估领域术语理解能力
模型大小 模型越大不一定越好，需要考虑 GPU 显存和推理成本
最大输入长度 避免长文档中的关键信息被截断
排序效果 使用 MRR、NDCG@K 等指标进行比较
推理延迟 考虑 P95、P99 延迟以及并发吞吐量

例如，可以选择 BGE-Reranker、Qwen3-Reranker 等模型作为候选方案，但最终应该根据自己的业务数据集进行评测，而不是直接根据公开排行榜选择模型。

在工程层面，我会先通过混合检索召回 Top 50，再通过 Reranker 重排序选出 Top 5～10，最后送入 LLM。通过批量推理、结果缓存、限制候选数量以及模型量化等方式降低重排序的额外开销。

3. 上下文压缩是什么？为什么不能直接将所有检索结果交给 LLM？

即使检索到的文档整体与问题相关，其中也可能包含大量无关内容。如果直接将这些文档全部输入 LLM，不仅会增加 Token 消耗和推理延迟，还可能引入噪声，干扰模型生成正确答案。

上下文压缩就是在文档检索和答案生成之间，进一步提取与当前问题相关的信息。

上下文压缩主要分为两种方式：抽取式压缩直接保留原文中的关键句子，生成式压缩则使用模型对原文进行总结。

对于医疗知识库等高准确性要求的场景，我会优先考虑抽取式压缩，并保留原始文档引用，因为生成式压缩可能改变原始医学表述，甚至引入新的幻觉。抽取时也需要注意保留适用条件、例外情况和前后文。

Re-ranking 解决的是哪些文档更相关的问题，而 Context Compression 解决的是文档内部哪些内容更相关的问题。

五、在线更新与热启动

1. 如何设计一个“准实时”更新的 RAG 系统？

我会将整个系统拆分为离线数据处理链路和在线检索链路，通过消息队列将文档变更事件与索引更新过程解耦，从而避免文档上传、修改和删除操作阻塞在线问答服务。

整个流程可以分为四个阶段。

第一阶段：捕获数据变更。 当用户新增、修改或删除文档时，通过业务事件或者 CDC（Change Data Capture，变更数据捕获）机制产生变更事件，再将事件写入消息队列。为了避免数据库修改成功但消息发送失败，可以使用 Transactional Outbox 等机制保证事件可靠投递。

第二阶段：异步处理数据。 后台 Worker 消费消息，对新增或修改的文档进行解析、分块和 Embedding 计算。对于已经处理过的内容，可以通过内容 Hash 判断是否发生变化，避免重复计算。

第三阶段：增量更新索引。 通过 Upsert 操作更新向量索引和关键词索引，而不是每次修改都重新构建整个索引。需要结合文档 ID、Chunk ID 和 Version 实现幂等处理，防止消息重复消费和旧消息覆盖新数据。

第四阶段：保证数据一致性。 只有当新版本所需的索引更新完成后，才将其标记为当前可检索版本。对于失败的更新任务，通过重试机制、死信队列和定期数据校验进行补偿。

这里采用的是最终一致性架构，允许新增或修改的文档在短时间内尚未进入检索系统，以换取系统吞吐量、可扩展性和稳定性。

2. 当文档被删除或下线时，如何确保检索结果不会继续引用它？

这是 RAG 数据一致性中非常重要的一个问题。如果只删除原始数据库中的文档，但是没有及时删除对应的向量数据，检索系统就可能继续召回已经失效的信息，这就是所谓的僵尸数据问题。

这样即使异步删除任务出现延迟或失败，也可以避免后续请求继续使用已经失效的知识。

3. 如何实现索引热启动？

如果向量索引规模非常大，服务每次重启时都重新构建索引，会产生很长的不可用时间。

因此，我会采用索引持久化、快照恢复、增量日志回放以及预热机制。

技术 作用
索引持久化 将已经构建好的索引保存到磁盘
Snapshot 快照 保存某一时刻的完整索引状态
WAL / 增量日志 记录快照之后发生的数据变更
mmap 内存映射 对支持该机制的索引减少初始加载开销
索引预热 提前加载热点数据，减少首次查询延迟
双索引切换 在后台构建新索引，完成后切换流量

对于全量重建，我不会直接删除旧索引再创建新索引，而是采用类似蓝绿部署的方式。

在线请求继续访问旧索引，同时在后台构建新索引。在新索引构建完成后，通过增量日志追平数据差异，进行一致性校验和性能测试，再通过索引别名或路由配置进行原子切换。旧索引可以暂时保留，以便出现问题时快速回滚。

需要注意的是，mmap 并不意味着所有索引都可以秒级恢复，具体恢复速度取决于索引格式、向量库实现、磁盘性能和数据规模。

综合题：如果让你从零设计一个生产级 RAG 系统，你会怎么设计？

如果让我设计一个生产级 RAG 系统，我会将系统拆分为离线索引、在线检索、答案生成和数据更新四个核心模块。

在离线索引阶段，我会根据文档结构采用语义边界结合固定长度的分块策略，通过 Chunk Size 和 Overlap 保证语义完整性，再使用 Embedding 模型生成向量，并构建 HNSW 向量索引和 BM25 倒排索引。

在在线检索阶段，我会采用混合检索架构，通过异步并行的方式同时执行关键词检索和向量检索，再使用 RRF 算法融合两路结果，解决不同检索器评分体系不一致的问题。

在精细排序阶段，我会引入 Cross-encoder 类型的 Reranker，对初步召回的候选文档进行重新打分，然后通过上下文压缩减少无关信息和 Token 消耗，最终将高质量的上下文交给 LLM 生成答案。

在数据更新方面，我会通过消息队列实现异步增量更新，使用文档版本号、幂等机制和逻辑删除保证数据一致性，并通过索引快照和双索引切换实现快速恢复和不停机重建。

最后，在系统性能方面，我会通过并行检索、批量推理、缓存、超时降级等手段控制延迟，同时建立离线评测和在线监控机制，在检索准确率、答案质量、系统延迟和资源成本之间进行平衡。
