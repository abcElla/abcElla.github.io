Agent的核心定义

AI Agent（智能体） 是一个具备以下三大能力的智能系统：

  1. 自主感知 ：能够理解当前环境和任务需求
  2. 自主决策 ：能够制定执行计划并动态调整
  3. 自主执行 ：能够调用工具完成实际任务

用一句话总结：Agent = LLM（大脑） + 工具（手脚） + 记忆（经验） + 规划（智慧）

Agent的整体架构

分为四个核心层：

  1. 感知层
    1. 作用：接收并理解用户输入
    2. 组件：用户输入→大语言模型理解
    3. 类比：耳朵和眼睛
  2. 认知层
    1. 作用：分析、推理、规划
    2. 组件：LLM Brain+规划模块+推理引擎
    3. 类比：大脑
  3. 执行层
    1. 作用：调用各种工具完成任务
    2. 组件：工具集（搜索、代码、API等）
    3. 类比：手脚
  4. 记忆层
    1. 作用：存储和检索信息
    2. 组件：短期记忆+长期记忆
    3. 类比：记忆系统

例子

用一个具体例子说明数据如何在架构中流转：

任务 ：「找出2024年诺贝尔物理学奖获得者，并总结他们的主要贡献」

这个过程中， Agent不是一次性生成答案 ，而是 通过多轮思考-行动-观察的循环 ，逐步接近最终答案。这就是Agent比传统LLM强大的地方。

规划模块

为什么需要规划？

举个例子：如果任务是「帮我准备一场技术分享会」，没有规划的Agent会：

  • 不知道从哪开始
  • 可能遗漏重要步骤
  • 浪费大量token重复思考

有规划的Agent会：

  • 确定主题和目标听众
  • 搜索相关技术资料
  • 设计PPT大纲
  • 准备演示Demo
  • 生成演讲稿

两种主流规划方法

方法一：ReAct框架（边想边做）

ReAct特点 ：

  • ✅ 灵活：可以根据中间结果调整计划
  • ✅ 适合探索性任务
  • ❌ Token消耗大：每一步都要调用LLM

方法二：Plan-and-Execute（先计划后执行）

Plan-and-Execute特点 ：

  • ✅ 高效：只需调用一次LLM规划
  • ✅ 可并行执行多个任务
  • ❌ 不灵活：难以根据中间结果调整

对比：

维度 ReAct Plan-and-Execute
核心思想 边想边做、走一步看一步 先全局规划、后集中执行
规划时机 动态、每步都重新决策 静态、一次性生成完整计划
灵活性 极高，实时调整、应对意外 低，计划固定，难应变
执行效率 慢（每步都要 LLM 推理） 快（执行阶段无思考，可并行）
LLM 调用 多（每轮都调）、成本高 少（仅规划 + 汇总）、成本低
错误处理 即时修正、不易跑偏 计划错则全错，需重规划
上下文 持续膨胀、长任务易超限 规划后上下文轻量、稳定
适用场景 探索、不确定、需实时调整 结构化、流程固定、长任务

选择建议

  • 探索性任务 （不知道中间会遇到什么）→ 用ReAct
  • 流程明确的任务 （步骤固定）→ 用Plan-and-Execute
  • 复杂混合任务 → 两者结合

多Agent关键挑战

挑战1：通信开销

多个Agent之间需要频繁通信：

其他解决方案：

  • 中心化调度（Supervisor）： 引入一个主 Agent，负责统一分配任务、收集结果，避免所有 Agent 之间两两通信。
  • 上下文压缩： Agent 之间只传递必要的任务信息、结构化数据和结果摘要，而不是完整的历史对话。
  • 共享状态（Shared State）： 将中间结果存储在共享内存、Redis 或数据库中，其他 Agent 按需读取，减少重复传输。
  • 异步通信： 使用消息队列或事件驱动机制，让没有依赖关系的 Agent 并行执行，减少同步等待时间。

全连接架构的潜在通信关系数量为 O(N2)O(N^2)O(N2)，中心化架构则可以降为 O(N)O(N)O(N)，但实际消息数量仍取决于业务流程，并且需要注意中央协调者的性能瓶颈。

挑战2：死锁和循环依赖

其他解决方案：

  • 有向无环图（DAG）： 将任务及其依赖关系构建成有向无环图，通过拓扑排序确定执行顺序，在调度前检测循环依赖。
  • 超时与重试机制（Timeout & Retry）： 为 Agent 设置最大等待时间，超过时间后取消任务、有限重试或执行降级策略。
  • 最大迭代次数： 限制 Agent 之间的交互轮数、任务递归深度，避免反复调用形成无限循环。
  • 统一任务调度： 由 Supervisor 管理任务执行状态，只有当前置依赖任务完成后，才允许下游任务执行。

需要注意，DAG 主要用于解决任务依赖层面的循环问题。如果 Agent 之间还存在共享资源的竞争，则需要结合统一加锁顺序、锁超时等机制防止资源死锁。

挑战3：结果冲突

其他解决方案：

  • 投票机制（Voting）： 让多个 Agent 独立生成结果，通过多数投票或加权投票选择最终答案，适合分类、选择等任务。
  • 裁判机制（LLM-as-a-Judge）： 引入独立的 Judge Agent，根据事实准确性、逻辑合理性、证据充分性等维度评估不同结果。
  • 辩论机制（Multi-Agent Debate）： 让多个 Agent 相互审查、质疑和修正对方的结论，在有限轮次内尝试达成共识。
  • 外部事实验证： 通过 RAG 知识库、数据库、搜索引擎或工具调用验证 Agent 的输出，避免多个 Agent 同时产生相同的幻觉。
  • 人工介入（Human-in-the-Loop）： 当结果存在严重冲突或涉及高风险决策时，交由人工进行最终审核。

多数投票并不意味着结果一定正确，因此对于医学、金融等高风险场景，应优先采用外部事实验证和人工审核。
